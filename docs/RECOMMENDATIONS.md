# 원티드의 다른 공고 추천

## 사용자 흐름

경험을 포함한 실제 분석이 성공하면 보고서는 바로 표시되고, 마지막의 **나의 경험과 연결되는 다른 회사** 영역이 별도 `/api/recommendations` 요청을 시작합니다. 서로 다른 회사의 공고를 최대 3개 표시합니다. 원문 링크, 지원 버튼 확인 여부, 확인 시각, 경험/공고 인용 쌍, 연결에 대한 해석, 희망 조건의 확인 여부를 구분합니다. 적합도 점수나 합격 가능성은 만들지 않습니다.

추천 검색 실패·취소·시간 초과는 이미 완성된 보고서를 변경하지 않습니다. 추천만 다시 검색할 수 있습니다. 경험 없이 분석한 경우, 가상 예시, 이력서 원문과 확인 서명이 없는 과거 기록에는 개인화된 추천을 만들지 않고 경험을 추가해 다시 분석하도록 안내합니다.

검색은 **분석에 제출했던 경험의 스냅샷**과 analysisId에 연결됩니다. 다른 보고서를 열 때 현재 편집 중인 이력서를 재사용하지 않습니다. 탭 전환은 새 검색을 만들지 않고, 동일 보고서를 다시 열면 5분 동안 메모리에 보관한 결과를 재사용합니다. 사용자가 직접 다시 검색하면 캐시를 우회합니다.

## 조사와 검증

1. 웹 도구 없는 모델 호출로 실제 경험과 명시한 희망 조건에서 직무·기술 검색어를 최대 3개 추출합니다. 연락처·URL을 먼저 제거하고 이름·주소·성별·건강 등 비직무 정보를 검색어에서 제외하도록 지시합니다. 검색어 형식도 검사하지만 완전한 자동 익명화를 보장하지 않습니다.
2. 웹 검색이 있는 별도 호출에는 검색어와 현재 공고 제외 정보만 전달합니다. 원본 이력서는 보내지 않습니다. 검색 도메인은 `wanted.co.kr`로 제한합니다. 출력에 URL만 적힌 것은 출처로 인정하지 않고 실제 검색 도구의 sources/annotations에 등장한 정확한 공고 URL만 후보로 받습니다.
3. 최대 8개 후보의 원티드 페이지를 동시에 최대 3개씩 가져옵니다. 허용 도메인/경로/포트와 리디렉션의 동일 공고 ID를 검사하며 외부·내부망 주소로 이동하지 않습니다. 본문은 최대 1MB, 페이지별 7초로 제한합니다. 회사/직무, 본문, JobPosting 메타데이터, 명시적 마감 문구, 마감일을 확인합니다. 날짜만 적힌 마감일은 한국시간 하루의 끝까지로 처리합니다.
4. 실제 확보한 후보 원문과 해당 분석의 이력서를 웹 도구 없는 모델로 대조합니다. 두 원문에 모두 존재하는 정확한 인용 쌍이 없는 후보를 제거합니다. 현재 회사와 중복 회사도 제외합니다. 희망 조건의 인용·공고 근거를 따로 검사하고, 확인 근거가 없는 조건은 미확인으로 둡니다. 근거가 연결된 필수 조건 충돌은 후보에서 제외합니다.

인용 일치 검사는 문구의 존재를 검증하는 것이며 의미적 적합성 전체를 보장하지 않습니다. 부정 표현, 요건의 실제 수준, 조건 적용 범위는 사용자가 원문에서 확인해야 합니다. 프롬프트는 AI 도구 사용을 자율 에이전트 구축으로, 개발 협업을 직접 구현으로 확대하지 못하도록 명시합니다.

## 채용 상태의 표시 기준

HTTP 200이나 검색 결과 노출만으로 **채용 중**이라고 표시하지 않습니다. 원문에서 활성화된 지원 버튼을 확인하면 **지원 버튼 확인 · 접수 여부 재확인 필요**, 그 외 본문만 확인되면 **공고 원문 확인 · 채용 상태 확인 필요**로 표시합니다. 닫힌 공고나 과거 마감일이 확인되면 제외합니다. 지원 버튼이 있어도 실제 접수 가능성을 보장하지 않습니다.

로그인·봇 차단·클라이언트 전용 렌더링 등으로 직접 원문을 확보하지 못한 후보는 추천하지 않습니다. 따라서 결과가 적거나 없을 수 있으며, 이는 적합한 회사가 없다는 의미가 아닙니다. 추측으로 개수를 채우거나 접근 제한을 우회하지 않습니다.

## API·모델·비용

기존 `/api/job`에서 발급한 `X-KnowBoth-Job-Proof`를 검증하고, 변경되지 않은 정규 원티드 공고와 필수 경험 입력만 받습니다. 동일 출처 Origin, JSON 형식, UTF-8 본문 170,000바이트 제한을 확인합니다. API 응답은 `Cache-Control: no-store`입니다.

추가 모델은 도입하지 않습니다. 기존 `OPENAI_API_KEY`, `OPENAI_MODEL`을 사용하고 기본값도 기존 앱과 동일합니다. 채팅창의 모델 변경이 배포 환경변수를 바꾸지는 않습니다. Responses API의 웹 검색과 구조화 출력을 지원하는 모델이 필요합니다.

추천 1회당 정상 경로는 계획·검색·대조의 최대 3회 모델 호출입니다. 후보가 없으면 대조 호출을 생략합니다. 내부 무제한 재시도는 없고, 사용자 재검색은 추가 비용을 발생시킵니다. 각 모델 단계는 18/35/28초, 서버 전체는 110초, 함수 maxDuration은 120초입니다. 클라이언트도 120초 후 취소합니다. 실제 함수 실행 한도는 배포 설정을 따릅니다.

현재 앱과 마찬가지로 로그인·영구 서버 캐시·분산 요청 제한은 없습니다. Job proof는 사용자 인증이나 비용 제한을 대체하지 않습니다. 공개 운영 시 방화벽·요청 제한·사용량 경보를 별도로 적용해야 합니다. 검증 과정에서 이력서, 서명, API 키를 로그에 남기지 않습니다.

## 개인정보와 보관

파일 원본은 브라우저에서 읽고, 추출 경험 텍스트는 기존 분석과 추천 대조를 위해 서버/AI 제공자에 전달됩니다. 모델 요청에는 `store: false`를 지정합니다. 제공자 자체 보존 정책까지 없애는 설정은 아닙니다.

추천 요청에 필요한 이력서 스냅샷과 서명, 실시간 추천 결과는 브라우저 메모리에만 둡니다. 신규 추천 데이터는 `localStorage`나 서버 DB에 저장하지 않습니다. 기존 보고서의 최근 기록 및 PDF 스키마는 변경하지 않으며, **추천 영역은 현재 PDF/최근 기록에 포함되지 않습니다**. 기존 기록 자체에는 기존 정책대로 경험 인용이 남을 수 있습니다.

## 회귀 방지

`npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`를 CI에서 실행합니다. 추가 테스트는 허용 URL, 실제 검색 출처, 원문/프로필 인용, 중복·마감·조건, 검색 단계의 데이터 분리, 본문 제한, 취소, API 서명/입력 검증, 업스트림 오류를 다룹니다. 모델과 네트워크는 테스트에서 모의 처리하므로 실제 유료 모델 호출의 성공이나 현재 공고의 접수 상태를 보장하지 않습니다.

관련 입력 경로도 보완했습니다. 공유 문구를 입력하는 필드는 브라우저 URL 유효성 검사에 막히지 않으며, wntd.co 단축주소를 정규 `/wd/숫자` 주소로 해석한 뒤 기존 검증에 전달합니다. PDF는 최대 4개 페이지를 동시 처리하고 원래 페이지 순서와 실제 줄바꿈을 유지합니다. 페이지 실패 시 이미 시작한 처리를 정리한 뒤 문서를 해제합니다. 이는 리소스 사용 개선이며, 모든 PDF의 읽기 시간이나 오류 해소를 보장하지 않습니다.
